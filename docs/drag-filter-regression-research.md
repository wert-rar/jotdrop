## Новый подтверждённый механизм зависания

Текущий render блокируется только при reordering. Флаг устанавливается в performCardMove после drop. Состояние draggedPath устанавливается раньше, в dragstart, но render его не проверяет. После завершения чтения проверяются только номер запроса и cardsVersion; затем renderCards очищает gridEl. Получается промежуток, когда пользователь уже несёт карточку, а обновление может удалить её DOM. Источники: [reordering](../src/customizations.js#L343), [guard render](../src/customizations.js#L544), [dragstart](../src/customizations.js#L600), [проверка чтения](../src/view.ts#L762), [очистка](../src/view.ts#L780).

Это проверено отдельным диагностическим сценарием [scripts/probe-drag-filter.cjs](../scripts/probe-drag-filter.cjs): настоящий Edge drag, production bundle, DOM/CSS, шесть однотипных заметок; файловые операции Obsidian заменены mock. Исследовательский скрипт не пишет реальные заметки и не меняет исходники плагина.

| Сценарий | Наблюдение |
| --- | --- |
| `control` | trusted dragstart → drop → dragend; карточка в колонке 1, состояние переноса очищено. |
| `refresh-during-drag` | render вызван после собственного обработчика dragstart; исходная карточка отсоединена, draggedPath ещё задан. Получен только trusted dragstart; native drag не завершился до ограничения 12 секунд. |
| `refresh-deferred` | Только в стенде render отложен до dragend. На запросе карточка остаётся подключённой; затем приходят trusted drop и dragend, карточка сохранена в колонке 1, reordering выключен. |
| `sort-load` | created-desc → фильтрация → перенос/manual → дозагрузка: 120 уникальных карточек, 0 колонок с нарушенным порядком. Гипотеза старого порядка дозагрузки в этом сценарии не подтвердилась. |

Команды воспроизведения из корня репозитория:

```powershell
node scripts/probe-drag-filter.cjs control
node scripts/probe-drag-filter.cjs refresh-during-drag
node scripts/probe-drag-filter.cjs refresh-deferred
node scripts/probe-drag-filter.cjs sort-load
```

Это диагностический отчёт, а не тест с verdict по exit code: смотреть JSON-поля blocked/events. Для зависания скрипт закрывает свой браузер через 12 секунд. Логи: work/logs/research-drag-control.log, research-drag-active-refresh.log, research-drag-deferred.log, research-drag-sort-load.log.

## Границы вывода

- Воспроизведён механизм, соответствующий симптому зависания и отсутствию drop. Ещё не доказано, что именно он срабатывает в пользовательском Obsidian: реальный источник refresh не зафиксирован.
- Отсутствие guard по draggedPath было и в c634354. Это уязвимое место до фильтров; изменения жизненного цикла сетки могли его проявить, но конкретный первый ломающий коммит не установлен.
- Успешные записи в старом журнале не опровергают сценарий: при отмене до drop performCardMove и запись вообще не начинаются.
- Отложенный render — причинный эксперимент в стенде, не готовое исправление. Он не закрывает чтение, начавшееся до dragstart и завершившееся во время него.
- Новое поведение не добавлялось в установленный кандидат во время пользовательской проверки.

## Рекомендуемое следующее изменение

Если пользовательский перенос остаётся сломанным, проверять защиту всего интервала dragstart → dragend. Нужно отложить новые refresh и принятие уже начатого чтения; доставить отложенное обновление после завершения или отмены drag, согласовав его с reordering/orderQueue. Не ограничиваться guard при входе в render: чтение могло начаться раньше.

До установки такого исправления закрепить три native-сценария: refresh после dragstart, завершение ранее начатого чтения во время drag, отмена drag без drop. Не заменять перенос прямым вызовом moveCard — он пропускает подтверждённое зависание до drop.
